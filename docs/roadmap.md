# mirucord ロードマップ

まだ作っていない機能と、その要件だけを書く。作り終えた機能はここから消す。
規模と性能の前提は AGENTS.md「想定規模と性能要件」に従う。

## 検索の保存先を R2 に移す

鯖ごとの Durable Object に置いている本文と索引を R2 に移す。

1 つの鯖に同時 1,000 件の検索が来ても、検索どうしが待ち合わない。
検索の対象は鯖の過去全部で、各リクエストは 3 分以内に返す。
一定時間で終わらない検索は、途中で ID を返し、その ID で呼び直してもらう。MCP の tasks 拡張は前提にしない。
本文はギルドの鍵で暗号化したまま置き、索引には HMAC 化した断片だけを置く。
編集・削除・投稿者の削除依頼は、検索結果からすぐ消える。実データも削除依頼の期限内に消える。
費用は Worker の CPU と読み取りを含めて小さくする。R2 の低頻度アクセスのクラスと Vectorize は使わない。

## 自然言語の検索

言葉が一致しなくても意味の近いメッセージを返す検索を、言葉で探す検索とは別のツールとして足す。
対象は言葉で探す検索と同じく、MCP を使う人が Discord 上で閲覧できるチャンネルの、鯖の過去全部とする。

Vectorize は使わない。問い合わせ費が「検索回数 × 次元数」に比例し、想定規模では最大の費目になるためである。
ベクトルは鯖ごと・期間ごとに分けて R2 に置き、期間の中は近いもの同士の塊にさらに分ける。検索では検索語に近い塊だけを読み、Worker で距離を計算する。R2 の往復は、塊を読む 1 回と本文を読む 1 回の 2 回にする。
期間はメッセージの作成時刻で区切る。今の期間は件数が少ないので、塊へ分けず全件と距離を計算する。過ぎた期間には新しいメッセージが入らないが、編集と削除は続く。そこで過ぎた期間のファイルは変更のたびには書き直さず、変化を小さな「最近の変更」ファイルと「無効の一覧」に積む。変化がたまったらその期間のファイルを書き直し、古い期間はまとめて 1 回の検索で読むファイル数が増え続けないようにする。

ベクトルからは元の文がある程度推測できるので、塊のファイルはギルドの鍵で暗号化して置き、Worker で復号してから計算する。
埋め込みはメッセージを取り込むときに 1 回だけ作る。検索語の埋め込みは検索のたびに要るので、同じ検索語の結果をキャッシュする。

埋め込みのモデルは、このリポジトリで日本語の検索に使って確かめた Workers AI の bge-m3（1,024 次元）にし、ベクトルは int8 に量子化して置く。
塊への分け方は k-means にし、期間が過ぎたときに Queue の consumer で作る。npm の既存ライブラリを使い、別のサーバーは置かない。
近い塊を全体の 5% ほど見る設定から始める。本番のデータで、全件と比べた上位 10 件の一致率が 9 割を下回るなら、見る塊を増やす。

## 課金

Developer Policy 18 は API Data の販売・商業化を禁じる。課金は機能（プランに含む DL 回数、または DL の権利の都度購入）に付け、データの件数に値段を付けない。
Developer Policy の Monetization Requirements は、Premium Apps の対応地域で有料機能を Discord 経由でも同価格以下で売ることを求める。日本は対象外だが、「地域」が開発者と購入者のどちらを指すかは規約から決められないので、併設するかを決める。

## Message Content intent の審査

利用者が 1 万人を超えると Message Content intent は審査制になり、毎年再審査がある。審査で用途とデータの扱いを説明できるようにする。
