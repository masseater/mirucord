# mirucord ロードマップ

mirucord は、Discord のサーバーを読むだけの MCP サーバーをホスティングで提供するサービスである。
コードと IaC はすべて公開し、運営を信用しない人は自前で動かせるようにする。

## 検索の保存先の設計（決定、未実装）

2026-10-12 に、検索の保存先を鯖ごとの Durable Object から R2 に移すと決めた。前提は AGENTS.md「想定規模と性能要件」である。

### R2 にする理由

Durable Object は鯖ごとに 1 本で順番に処理する。最大の鯖に同時 1,000 件の検索が来ると、過去全部を対象にした検索では後ろのリクエストが数十分待つ見込みになる。R2 なら同じ鯖への検索どうしが待ち合わない。
応答時間の要件は 3 分以内なので、R2 を読む往復の遅さは問題にならない。反映の遅れも要件にないので、書き込みは数分ごとにまとめられる。
費用の大半を占めるのは、保存よりも呼び出しごとの費用（Worker の CPU と読み取り）である。R2 は書いたあと変えないファイルを Cache API に載せられ、キャッシュに当たった読みは課金されない。MCP の呼び出しはほぼ同じ地域の Worker に来るので、キャッシュが効きやすい。

### 索引と本文の置き方

索引と本文は鯖ごとに分け、検索は 1 つの鯖の中で行う。
索引は、今と同じ HMAC 化した 1〜3 文字の断片（トークン）ごとに、それを含むメッセージ ID の一覧を持つ。トークンの先頭のビットで数百のファイルに振り分ける。本文は、ギルドの鍵で暗号化したまま、時間で区切ったファイルに置く。
新しいメッセージは、数分ごとにまとめて小さな「最近の分」ファイルへ書く。締まった期間のファイルは書き換えず、古くなったら大きな期間にまとめ直して、1 回の検索で読むファイル数が増え続けないようにする。どのファイルがあるかの一覧はキャッシュか D1 に置き、毎回 R2 から読まない。

### 検索の流れ

R2 の往復は 2 回にする。1 回目は、検索語のトークンが入っている索引ファイル、「最近の分」、無効の一覧を並列に読み、ID を掛け合わせて鯖の過去全部から該当を出す。2 回目は、返す分のメッセージが入った本文ファイルを並列に読み、復号して照合する。
一定時間で終わらない検索は、途中で ID を返し、その ID で呼び直してもらう形をツールの決まりとして作る。MCP の tasks 拡張は、2026-10 時点で ChatGPT・Claude Code・Cursor・OpenCode などの主要なクライアントが対応していないので前提にしない。

### 編集と削除

編集されたメッセージは、新しい本文を「最近の分」に入れ、古い本文の ID を鯖ごとの「無効の一覧」に足す。検索では古いファイルから出た結果をこの一覧で除く。
削除と投稿者の削除依頼も同じ一覧に足すので、検索からはすぐ消える。実データは、まとめ直しのときと削除依頼の期限内に、該当するファイルを書き直して消す。書き直したファイルは新しい名前で置き、古いキャッシュは参照されないまま期限切れで消える。
本文を投稿者ごとの鍵で暗号化し、削除依頼でその鍵を捨てる案（暗号学的消去）もある。これならファイルの書き直しを待たずに読めなくなる。

### 使わないもの

R2 の低頻度アクセスのクラスは使わない。過去全部を検索するので古いファイルも毎回読まれ、保存の単価より読み 1 回の単価の高さが効くためである。
Vectorize も使わない。問い合わせ費が「検索回数 × 次元数」に比例し、想定規模では最大の費目になるためである。

## 検討事項

次を決める。

| 項目                   | 決めること                                                                                                                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課金の単位             | Developer Policy 18 は API Data の販売・商業化を禁じる。課金は機能（プランに含む DL 回数、または DL の権利の都度購入）に付け、データの件数に値段を付けない                                                                         |
| Premium Apps の併設    | Developer Policy の Monetization Requirements は、Premium Apps の対応地域で有料機能を Discord 経由でも同価格以下で売ることを求める。日本は対象外だが、「地域」が開発者と購入者のどちらを指すかは規約から決められない               |
| ベクトル検索           | 自然言語の検索を足すなら、Vectorize ではなく R2 にベクトルを鯖ごと・期間ごとの塊に分けて置き、近い塊だけを読んで Worker で距離を計算する形にするか。近似になること、塊への分け方を自作するか別のサーバーで作ることを含めて決める   |
| Message Content intent | 利用者が 1 万人を超えると審査制になり、毎年再審査がある。審査で用途とデータの扱いを説明できるようにする                                                                                                                            |
| ドメイン               | 本番を masseater.dev のサブドメインのまま続けるか、mirucord 専用のドメインを取るか。決まったら、そのドメインで Developer Portal の Privacy Policy URL と Terms of Service URL を設定する（Developer Terms of Service 5(a) の義務） |
